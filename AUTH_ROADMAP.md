# Практика backend-аутентификации и авторизации

Рабочий учебный маршрут для этого NestJS-проекта. Обновлён 30 октября 2026 года.

**Цель:** самостоятельно построить и понять систему с email + паролем, телефоном + SMS-кодом, Google и GitHub; разобраться в JWT, серверных сессиях, правах, восстановлении доступа, БД, Redis и эксплуатации.

## Правила работы

1. **Весь код пишет пользователь:** приложение, тесты, миграции, конфигурацию и исправления. Ассистент читает и проверяет код, объясняет, даёт подсказки и примеры в чате. Самостоятельно реализацию не меняет. Этот план можно редактировать по договорённости.
2. Одно занятие — одна небольшая задача с ID из плана. Сначала объясняем, зачем она нужна, затем реализация пользователем, проверка и отметка результата. Не выдаём весь этап одним заданием.
3. Теория появляется перед использованием: DTO при входе, транзакции при создании сессий, Redis при общих лимитах нескольких серверов. Большого предварительного экзамена нет; короткая проверка понимания — по необходимости, без бесконечной цепочки вопросов.
4. Примеры кода можно просить в чате. Разбираем предложенный код и переносим его самостоятельно.
5. Не меняем следующий шаг на ходу. Новая зависимость или обнаруженная ошибка сначала получает объяснение и место в плане. Не добавляем инфраструктуру ради инфраструктуры.
6. Тестируем вместе с функцией, а не только в конце. Unit проверяет логику, integration — реальные ограничения и транзакции БД, browser/e2e — весь обмен. Мок repository не доказывает отсутствие гонки.
7. `[x]` означает подтверждённый результат; `[ ]` — работа впереди. Различаем «обсудили», «видно в коде», «проверено пользователем» и «проверено тестом». Не закрываем большой этап по одному успешному запросу.
8. До итогового этапа используем локальный стенд и учебные данные. Промежуточная версия может намеренно не иметь следующих механизмов; её ограничения всегда указаны. Реальные платные отправки и production-публикация в учебные шаги не входят автоматически.

## Решения, которые сохраняем по всему маршруту

- Access — короткоживущий подписанный JWT; в браузере хранится в памяти и передаётся через `Authorization: Bearer …`. Refresh — длинный криптографически случайный непрозрачный токен, не обязательно JWT; передаётся в `HttpOnly` cookie.
- Браузерные атрибуты cookie, CORS и CSRF проектируем до подключения refresh к браузеру. `HttpOnly` — атрибут cookie, а не отдельное хранилище. Он мешает чтению cookie из JS, но не устраняет XSS.
- PostgreSQL — источник истины для пользователей, сессий, поколений refresh и связей с провайдерами. Сначала делаем без кеша авторизации. Redis вводим для распределённых лимитов; перенос остальных данных требует отдельной причины.
- С этапа 5 каждый защищённый запрос проверяет актуальную сессию и состояние аккаунта в БД. Роли для принятия решений тоже читаем из актуального состояния. Это намеренный stateful-вариант с понятным отзывом; позже сравним цену и альтернативы.
- Все способы входа после проверки credentials вызывают один механизм создания собственной сессии. Токен Google/GitHub не заменяет токен нашего API.
- Длинный случайный token хранится через verifier, например SHA-256; пароли — через адаптивный password hash. Короткий OTP требует отдельной защиты от перебора и verifier с отдельным серверным ключом. Нельзя принимать verifier вместо исходного секрета.
- Email verification, reset, login, link и MFA — разные назначения. Секрет одного назначения не даёт доступ к другому.
- Точные TTL и лимиты записываем при реализации: значение, причина, ожидаемый риск. Для первых экспериментов access может жить 5–15 минут; это не универсальная рекомендация для любого продукта.

- [ ] **5.2** Добавить состояния пользователя active/blocked/deleted и миграцию; определить отказ login и реакцию на уже выданные токены. Неподтверждённый email пока не блокирует все функции: политику введём в 9.
- [ ] **5.3** Выделить общий сервис создания сессии; после успешного login создавать отдельную запись и добавлять `sid` в JWT. Ошибка выпуска/сохранения не должна давать клиенту пригодный частично созданный вход.

**Выход:** настоящий серверный logout. Учебные JWT предыдущего этапа без `sid` больше не принимаются; нужно войти заново. Refresh добавляем только следующим этапом.

## 6. Refresh с ротацией и безопасной доставкой

**Вход:** сессии и отзыв из 5. **Перед кодом:** CSPRNG, verifier случайного секрета, row lock/условный update, cookies и CSRF. Сначала согласовать браузерную топологию; до browser-клиента проверять HTTP-стендом.

- [ ] **6.1** Спроектировать `refresh_tokens`: public lookup ID, session/family, verifier, expiresAt, usedAt, revokedAt, successor. Семейство для начальной реализации соответствует сессии; задать срок хранения использованных поколений.
- [ ] **6.2** Выпускать ID + случайный secret; сохранять только verifier. Публичный ID помогает найти запись, но один не даёт доступа. Сравнивать verifier без утечки содержимого, с проверкой формата/длины.
- [ ] **6.3** Login создаёт сессию и первое поколение refresh согласованно. Access возвращается в body, refresh устанавливается cookie. Не выдавать refresh в URL, логах и публичном JSON-ответе браузеру.
- [ ] **6.4** Выбрать имя, host/domain/path и атрибуты cookie: HttpOnly, Secure для HTTPS, подходящий SameSite и срок. Зафиксировать локальные отличия; не отключать production-защиту ради localhost. Проверить доступность cookie на refresh и logout.
- [ ] **6.5** До cookie-endpoints подключить защиту от CSRF для выбранного размещения: проверка доверенного Origin и подходящая стратегия CSRF token. Обосновать SameSite; CORS не считать самостоятельной CSRF-защитой. Учесть login CSRF и OAuth callback отдельно.
- [ ] **6.6** `POST /auth/refresh`: проверить secret, expiry, сессию и аккаунт; в транзакции погасить старое поколение и создать новое, затем выдать новый access и cookie. Блокировку/условный update выбрать явно.
- [ ] **6.7** Валидный повтор использованного секрета → отзыв семейства и событие replay. Неверный secret к известному ID → отказ без возможности отозвать чужую сессию.
- [ ] **6.8** Проверить границы транзакции replay: отзыв должен сохраниться, даже если HTTP-ответ — `401`. Исключение внутри транзакции не должно откатывать сам отзыв.
- [ ] **6.9** При logout отзывать всю текущую цепочку refresh и удалять cookie с теми же domain/path. Очистка cookie не заменяет отзыв в БД; ответ с токенами не кешируется (`Cache-Control: no-store`).
- [ ] **6.10** Integration на настоящем PostgreSQL: успешная ротация, истечение, replay, неверный secret, rollback и два одновременных refresh. Старое поколение не должно успешно породить два новых.

**Выход:** refresh одноразовый, отзыв работает, браузерная доставка и её защита спроектированы вместе. Политику одновременных вкладок проверяем в 7, не скрывая возможный принудительный повторный вход.

- [ ] **7.3** Реализовать single-flight refresh и один повтор исходного запроса; запретить бесконечный цикл refresh→401→refresh. Отдельно рассмотреть координацию нескольких вкладок.
- [ ] **7.4** Строгая начальная политика: повтор поколения завершает сессию. Проверить гонку вкладок и потерянный ответ после commit; записать UX-компромисс. Grace window/идемпотентность — отдельное улучшение с анализом replay-риска.

- [ ] **7.7** Browser/e2e: вход на двух клиентах, logout одного/всех, reload, expired access, expired refresh, чужой Origin, отсутствие CSRF-защиты в запросе, очистка cookie.

- [ ] **15.3** Проверять окно времени, replay TOTP, общий rate limit и атомарное потребление контекста. Не считать SMS-only вход MFA и не считать social login автоматически MFA.
- [ ] **15.4** Recovery codes показывать один раз, хранить verifier, расходовать атомарно; перевыпуск отзывает старые коды.
- [ ] **15.5** Отключение/смена MFA и step-up для admin/смены контактов требуют свежего подтверждения; определить безопасное восстановление без слабого обхода защиты.
- [ ] **15.6** Проверить все четыре способа первого входа, refresh после MFA, потерю устройства и replay кода. Обновление access не должно само повышать уровень или свежесть аутентификации.

**Выход:** незавершённый MFA-вход не открывает API; recovery не обходит политику защиты.

## 16. Политика и эволюция password hashing

**Вход:** несколько способов входа и восстановления работают; теперь можно проверить совместимость изменений алгоритма.

- [ ] **16.1** Сверить политику длины/распространённых и скомпрометированных паролей с актуальными рекомендациями; не требовать бессмысленную периодическую смену без причины. Не отправлять пароль внешнему сервису проверки.
- [ ] **16.2** Сравнить bcrypt и Argon2id: salt, CPU, memory, стоимость атаки и нагрузка на сервер. Измерить на целевом окружении, а не копировать cost вслепую.
- [ ] **16.3** Реализовать version-aware verify и rehash после успешного входа со старым хешем; не требовать знания всех исходных паролей для миграции.
- [ ] **16.4** Обновить регистрацию/reset/change password и dummy hash согласованно. Учесть конкурентную смену пароля при rehash: нельзя перезаписать новый пароль устаревшим хешем.
- [ ] **16.5** Тесты старого/нового формата, Unicode, политики длины, ошибочного пароля и rehash; нагрузка не должна исчерпывать worker pool/память.

**Выход:** алгоритм меняется без потери доступа и без ослабления новых/старых сценариев.

## 17. Доставка, события и наблюдаемость

**Вход:** email/SMS адаптеры и Redis уже используются. **Перед кодом:** внешний провайдер не участвует в SQL-транзакции; «отправлено» не равно «доставлено».

- [ ] **17.1** Описать сбои: БД commit прошёл, send упал; send прошёл, ответ потерян; challenge истёк в очереди. Ввести outbox в одной транзакции с изменением БД.
- [ ] **17.2** Добавить worker/очередь, например BullMQ, когда нужна повторная доставка: retry/backoff, idempotency key, failed jobs, bounded retries. Не обещать exactly-once внешнего эффекта.
- [ ] **17.3** Не хранить отправляемые секреты открыто в outbox/Redis: если их нужно повторно доставить, защитить payload шифрованием с отдельным ключом, TTL и удалением после отправки. Hash challenge не позволяет восстановить текст письма.
- [ ] **17.4** Повторная доставка не подтверждает аккаунт и не продлевает срок кода незаметно; устаревшие сообщения не отправлять. Проверять подписи webhooks провайдера и не доверять присланным статусам без проверки.
- [ ] **17.5** Расширить security events всех сценариев: actor/session, событие, время, результат, correlation ID; исключить cookies, Authorization, пароли, коды и полные токены.
- [ ] **17.6** Метрики latency/error rate, replay, login failures, backlog и стоимости SMS; алерты на осмысленные аномалии, права доступа и retention для персональных данных.
- [ ] **17.7** Проверить повтор worker job, падение после send, timeout провайдера, старый challenge в очереди и отсутствие секретов в логах/ошибках.

**Выход:** внешние сбои обрабатываются явно, пользователь не получает ложное подтверждение, секреты не переезжают из защищённой таблицы в открытые логи/очередь.

## 18. Эксплуатация: ключи, окружение, данные

**Вход:** завершённые прикладные сценарии. Отдельный этап перед размещением доступного извне стенда.

- [ ] **18.1** HTTPS/reverse proxy, доверенные forwarded headers, cookie Secure, CORS/CSRF, security headers и лимиты тела/таймаутов; локальные послабления не попадают в release config.
- [ ] **18.2** Сравнить HMAC и асимметричные ключи. Ввести `kid` и ротацию с периодом проверки старых токенов; доверенный набор ключей/JWKS, запрет произвольных URL из заголовка JWT.
- [ ] **18.3** Сценарий утечки signing key: экстренный отзыв ключа/сессий и повторный вход. Для симметричных ключей помнить: любой сервис с секретом может выпускать токены.
- [ ] **18.4** Secrets manager, разделение окружений, least privilege БД, сетевое закрытие Postgres/Redis, зависимостей и контейнеров; проверка версий/уязвимостей перед релизом.
- [ ] **18.5** Индексы и query plans auth-запросов, пул соединений, очистка истёкших challenges/сессий. Историю refresh не удалять раньше окна replay detection; последние активности не превращать в write bottleneck.
- [ ] **18.6** Backup и тест восстановления, retention/удаление PII, rolling release и совместимые миграции. Восстановление старой БД может воскресить отозванные сессии: предусмотреть массовую инвалидизацию.
- [ ] **18.7** Рассмотреть кеш auth-state только после замеров: источник истины, инвалидация и допустимое окно устаревших прав. Базовую реализацию с PostgreSQL сохранять как проверяемую модель.

**Выход:** задокументированы запуск, ротация, восстановление, очистка и реагирование; отзыв соответствует обещаниям при рестартах и отказах.

## 19. Итоговые сценарии и review

**Вход:** 0–18. Здесь собираем ранее написанные проверки, а не впервые начинаем тестирование.

- [ ] **19.1** На чистом окружении: migrations → register → confirm → каждый способ login → me → refresh → logout → logout-all.
- [ ] **19.2** Матрица доступа: анонимный/USER/ADMIN, blocked/deleted/unverified, владелец/посторонний, MFA pending/complete; проверка каждого HTTP-маршрута.
- [ ] **19.3** Настоящий Postgres: гонки регистрации, refresh/replay/revoke, reset/change, OTP, link/unlink и удаления последнего метода. Проверить итоговое состояние БД, не только HTTP-код.
- [ ] **19.4** Browser: cookies, CSRF, XSS-последствия, reload, две вкладки/устройства, потерянный refresh response, redirect и callback. Отдельно sandbox smoke Google/GitHub/email/SMS.
- [ ] **19.5** Учебные инциденты: кража access/refresh, компрометация signing key, недоступность БД/Redis/провайдера, рассинхронизация времени, роль отозвана при действующем JWT.
- [ ] **19.6** Нагрузочные проверки login/refresh, hash CPU/RAM, DB pool и Redis, очередь и бюджеты. Не генерировать реальные платные SMS в нагрузочном тесте.
- [ ] **19.7** README, HTTP-примеры без секретов, API-контракт, решения и ограничения, инструкции incident response. Сверить покрытие с выбранными требованиями актуального OWASP ASVS.

**Выход:** готовность к конкретному размещению оценивается по результатам тестов и review, а не по числу установленных библиотек или наличию JWT. Оставшиеся риски и незакрытые требования перечислены явно.

## 20. Расширения после основного маршрута

Выбираем по интересу или требованиям продукта; не вставляем внезапно между основными задачами.

- [ ] **20.1** Passkeys/WebAuthn: challenge, origin/RP ID, регистрация/вход, несколько credentials, потеря устройства и восстановление; подключение к общей сессии.
- [ ] **20.2** Email magic link/OTP: короткие коды против случайной ссылки, scanner-safe подтверждение, ограничения восстановления.
- [ ] **20.3** Permissions, несколько ролей, ABAC/policies и tenant isolation: составные ограничения в SQL, пользователь в нескольких организациях, приглашения.
- [ ] **20.4** Серверная cookie-сессия и BFF против JWT; opaque access + introspection, denylist/token version, измерение trade-offs.
- [ ] **20.5** Mobile: защищённое системное хранилище, OAuth callback/deep link, PKCE и отличие от browser-cookie модели.
- [ ] **20.6** API keys/scopes, service accounts, OAuth client credentials; человеческая сессия не подходит для всех машинных интеграций.
- [ ] **20.7** WebSocket/GraphQL/очереди: повторная проверка доступа, истечение/отзыв долгого соединения, политики вне HTTP-контроллера.
- [ ] **20.8** Готовый identity provider, SSO, федерация, sender-constrained tokens/DPoP; сравнить сложность своей системы с интеграцией провайдера.
